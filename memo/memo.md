# 1. QR 평가 제한 문제 파악 및 대안 검토

**2026-10-20 작성**

## 문제

예비군은 입소 시 **카메라 차단 앱**이 적용된다. 보안 정책이므로 평가를 위해
풀어 줄 수 없다. 따라서 **QR 코드를 쓸 수 없다.**

그렇다고 종이 평가지로 돌아가면 채점과 집계가 전부 수작업이 된다.
조별 평균을 내서 우수 조를 뽑아야 하는데, 수백 명분을 당일에 처리할 수 없다.

필요한 것은 **카메라를 거치지 않고 휴대폰에 주소를 전달하는 방법**이었다.

## 검토한 대안

| 대안 | 판단 | 사유 |
|---|---|---|
| QR 코드 | **불가** | 카메라가 차단됨. 정책상 해제 불가 |
| 주소 직접 입력 | 기각 | 수백 명이 긴 주소를 타자. 오타 처리가 더 큰 부담 |
| 단축 주소 | 기각 | 여전히 타자해야 하고, 단축 서비스가 중단되면 전체가 멈춤 |
| 문자 · 카카오 발송 | 기각 | 연락처를 수집해야 함. 개인정보 부담이 평가 목적에 비해 과도 |
| 부대 와이파이 접속 화면 | 기각 | 망 설비를 건드려야 하고 통제 범위를 벗어남 |
| **NFC 카드** | **채택** | 카메라와 무관. 태그 한 번으로 열림. 카드 재사용 가능 |

## NFC 를 고른 이유

- **카메라를 전혀 쓰지 않는다** — 차단 앱과 무관하게 동작한다
- **예비군이 할 일이 태그 한 번**이다 — 주소를 외우거나 입력할 필요가 없다
- **카드를 회차마다 재사용**한다 — 소모품이 아니다
- 아이폰 XS 이상은 **화면만 켜져 있으면** 자동 인식된다

## 지금 구축된 모습

```
 카드 태그            카드에는 '주소 한 줄'만 기록되어 있다
      │
      ▼
 부대 전용 페이지      GitHub Pages (무료 · 상시)
      │               예비군이 조·번을 한 번 고른다
      ▼
 배너 4개             안보교육 / 전투부상자처치 / 전시동원절차 / 설문
      │
      ▼
 구글폼               번호가 미리 채워진 상태로 열린다
      │
      ▼
 응답 스프레드시트      조별 평균 → 우수 조 자동 산출
```

### 카드에 번호를 넣지 않았다

가장 중요한 결정이다. 카드 500장이 **전부 똑같다.**

| | 번호를 넣는 방식 | 지금 방식 |
|---|---|---|
| 카드 종류 | 500종 (1-1 ~ 50-10) | **1종** |
| 조 편성 변경 시 | 500장 다시 기록 | **그대로 사용** |
| 카드 분실·혼동 | 그 번호를 쓸 수 없음 | 아무 카드나 사용 가능 |
| 번호 지정 | 카드가 결정 | 첫 화면에서 본인이 선택 |

번호는 예비군이 첫 화면에서 한 번 고르고, 그 뒤로는 폼에 **자동 입력**된다.
카드와 번호를 맞춰 배부할 필요가 없으므로 입소 절차가 단순해진다.

> 조별 카드를 따로 쓰고 싶으면 주소 뒤에 `?g=3` 을 붙여 기록하면 된다.
> 지금은 쓰지 않는다 — 카드를 1종으로 두는 이점이 더 크다고 판단했다.

### 주소를 깃헙 페이지에 둔 이유

구글 앱스스크립트로 첫 화면까지 만들 수도 있었지만, **동시 접속**이 문제였다.
수백 명이 한꺼번에 태그하면 앱스스크립트 쪽이 먼저 막힌다.

그래서 **첫 화면은 깃헙이 내려주고**(정적 파일, 동시 접속 제한 없음),
앱스스크립트는 열림·닫힘 상태 확인과 집계만 맡게 했다.
서버가 늦어도 화면은 즉시 뜬다.

## 확인된 제약 — 카드 구매·운용 시 주의

| 제약 | 내용 |
|---|---|
| 칩 종류 | **NTAG213 / 215 / 216 만 가능.** Mifare Classic 은 아이폰에서 읽히지 않는다 |
| 금속 | 철제 책상·캐비닛에 붙이면 인식되지 않는다. 카드로 배부한다 |
| 구형 아이폰 | 7 ~ X 는 제어센터에 `NFC 태그 리더` 를 추가해 실행해야 한다 |
| 안드로이드 | `설정 → 연결 → NFC` 가 켜져 있어야 한다 |
| 카드 잠금 | 되돌릴 수 없다. 주소가 확정된 뒤에만 잠근다 |

사무실에 흔한 출입증 계열이 대부분 Mifare Classic 이다. **`NTAG` 로 명시된
카드를 구매해야 한다.** 이 지점에서 실패하는 경우가 가장 많다.

## 대비책

카드가 인식되지 않는 경우를 대비해 **주소를 카드 뒷면에 인쇄**한다.
NFC 가 안 되는 구형 기종이나 카드 불량일 때 직접 입력으로 넘어갈 수 있다.

```
휴대폰 뒷면 윗부분에 카드를 대면 평가·설문 화면이 열립니다.
열리지 않으면: 설정에서 NFC 켜기 (아이폰은 화면만 켜면 됩니다)
그래도 안 되면 주소 직접 입력: <부대 주소>
```

## 결과

카메라 차단 상태에서 **QR 없이** 평가·설문이 동작한다.
예비군이 하는 일은 **카드 태그 → 조·번 선택 한 번 → 배너 누르기** 뿐이다.

# 2. NFC 카드 활용 평가 체계 구상

**2026-10-21 작성**

1번에서 **NFC 로 주소를 전달한다**는 것까지 정했다. 이 단계에서는 그 주소 뒤에
무엇을 둘지, 즉 **평가 체계 전체의 골격**을 정했다.

## 체계가 해야 할 일

| 요구 | 비고 |
|---|---|
| 평가 3과목 응시 | 안보교육 / 전투부상자처치 / 전시동원절차 |
| 자동 채점 | 당일에 결과가 나와야 한다. 수작업 채점은 불가 |
| 조별 평균으로 **우수 조** 선정 | 개인 시상이 아니라 조 단위 시상이다 |
| 무기명 설문 | 평가와 분리. 솔직한 응답을 받아야 한다 |
| 교관이 **열고 닫는다** | 통제 없이 열어 두면 무분별하게 제출된다 |

## 구상 1 — 사람을 무엇으로 식별할까

**`조-번` (m-n) 으로 정했다.** 이름·군번·연락처를 받지 않는다.

| 식별 방법 | 판단 |
|---|---|
| 이름 | 기각 — 동명이인. 개인정보를 받을 이유가 없다 |
| 군번 | 기각 — 입력이 길고 오타가 많다. 민감정보 |
| 연락처 | 기각 — 수집 근거가 없다 |
| **조-번** | **채택** — 당일 편성이면 충분하다. 시상 단위와 일치한다 |

시상 단위가 **조**이므로 개인을 특정할 필요가 애초에 없었다.
`3-7` 이면 3조의 득점에 더하는 것으로 충분하다.

훈련이 끝나면 조 편성 자체가 의미를 잃으므로, **남는 자료에 개인정보가 없다.**
이 점이 결정적이었다.

## 구상 2 — 평가지를 새로 만들지 않는다

구글폼 **퀴즈 기능**을 그대로 쓴다. 문항·정답·배점을 넣으면 **자동 채점**되고
응답이 스프레드시트로 쌓인다.

평가 화면을 직접 만들면 문항 편집기·채점·저장을 전부 만들어야 한다.
그 부분은 이미 있는 것을 쓰고, **없는 것만 만들기로** 했다.

| 구글폼이 해 주는 것 | 우리가 만들 것 |
|---|---|
| 문항 표시 · 답안 수집 | 첫 화면 (어느 폼으로 보낼지) |
| 자동 채점 · 점수 기록 | 조별 집계 · 우수 조 산출 |
| 응답 수락 열기/닫기 | 교관 화면 (언제 누가 열지) |
| 응답을 시트로 저장 | 번호 자동 입력 · 중복 처리 |

## 구상 3 — 세 겹으로 나눈다

한 군데에 몰면 **동시 접속**에서 막힌다. 역할을 셋으로 쪼갰다.

```
① NFC 카드          주소 한 줄.          변하지 않는다
       │
       ▼
② 첫 화면           깃헙 페이지(정적).   동시 접속 제한 없음
   (어느 폼으로)     수백 명이 한꺼번에 태그해도 즉시 뜬다
       │
       ▼
③ 앱스스크립트       열림·닫힘 상태 확인, 집계.
   (판단과 계산)      동시 처리 한계가 있으므로 꼭 필요한 일만 맡긴다
```

**원칙: 화면은 서버를 기다리지 않는다.** 상태 조회가 늦어도 첫 화면은 먼저
뜨고, 상태를 받으면 배너가 갱신된다. 수백 명이 동시에 들어오는 상황에서
"흰 화면"이 나오면 안 된다.

## 구상 4 — 무엇으로 실제로 막을까

열고 닫기를 화면에서만 처리하면, **주소를 아는 사람은 그냥 들어간다.**
그래서 차단 지점을 두 겹으로 나눴다.

| 겹 | 수단 | 성격 |
|---|---|---|
| 실제 차단 | 구글폼의 **응답 수락** 끄기 | 주소를 직접 열어도 제출 불가 |
| 안내 | 첫 화면 배너를 `마감`·`대기` 로 표시 | 헛걸음을 줄인다 |

**진짜 잠금은 구글폼 쪽**이고, 화면 표시는 안내다. 이 구분을 처음에 정해 두지
않으면 "닫았는데 들어가졌다" 는 사고가 난다.

## 구상 5 — 규모는 방어적으로

입소 인원은 회차마다 다르다. **50개 조 × 10명 = 500명**까지 동작하게 잡았다.

- 실제 참가가 328명이어도 그대로 쓴다. 빈 조는 집계에서 빠진다
- 조 평균은 **실제 응시인원**으로 나눈다. 조기 퇴소자 때문에 불리해지지 않는다
- 인원이 늘어도 설정값만 바꾸면 된다

## 구상 6 — 하루 단위로 끊는다

예비군은 날마다 다른 사람이 들어오고, **같은 사람이 다른 조·번**으로 들어올
수도 있다. 그래서 모든 것을 **날짜로 끊기로** 했다.

| 대상 | 하루가 지나면 |
|---|---|
| 번호 등록 | 비워진다. 어제 `3-7` 이던 사람이 오늘 `12-4` 로 들어와도 된다 |
| 평가·설문 개방 | 전부 닫힌 상태로 돌아간다 |
| 집계 | 그 날짜 기준으로 낸다. 과거 날짜는 따로 조회한다 |

**기본값은 전부 닫힘**이다. 열어야 열리는 것이지, 닫아야 닫히는 것이 아니다.
교관이 깜빡해도 다음 회차가 열린 채로 시작하지 않는다.

## 이 단계에서 정하지 않고 넘긴 것

구상 단계에서 결론을 미룬 것들이다. 뒤 단계에서 정했다.

| 보류한 것 | 어디서 정했는가 |
|---|---|
| 평가지를 A안·B안으로 나눌지 | 14단계 — 조별 `ABBA` 배정으로 결정 |
| 같은 번호가 여러 번 내면 어떻게 할지 | 17단계 — **처음 제출만** 인정 |
| 번호를 카드에 박을지 | 19단계 — **보류**. 카드 1종 유지 |
| 조별로 따로 열지 | 16단계 — 과목 × 조 단위로 개폐 |

## 결과

골격이 이렇게 정해졌다.

```
카드(주소) → 첫 화면(조·번 선택) → 구글폼(자동 채점) → 시트(조별 집계)
                    ▲                      ▲
                    └── 교관 화면 ──────────┘
                        (열고 닫기 · 현황 · 우수 조)
```

개인정보를 받지 않고, 평가지를 새로 만들지 않고, 동시 접속에 막히지 않는 구조다.

# 3. 평가·설문 홈페이지 요구사항 정리

**2026-10-22 작성**

2번에서 골격을 정했다. 이 단계에서는 **화면에 무엇을 넣고 무엇을 넣지 않을지**를
확정했다. 빼는 결정이 넣는 결정보다 중요했다.

## 화면을 둘로 나눈다

| 화면 | 보는 사람 | 성격 |
|---|---|---|
| `index.html` | 예비군 수백 명 | 극단적으로 단순. 설명 없이 쓸 수 있어야 한다 |
| `admin.html` | 교관 몇 명 | 기능이 많아도 된다. PIN 으로 막는다 |

한 화면에 섞으면 예비군 화면이 복잡해지고, 교관 기능이 노출된다.
주소부터 갈라 두면 섞일 일이 없다.

## 예비군 화면 — 넣을 것과 뺄 것

| 넣는다 | 이유 |
|---|---|
| 배너 4개 (평가 3 + 설문 1) | 누를 것이 넷뿐이면 설명이 필요 없다 |
| 조·번 선택 **1회** | 번호를 폼마다 입력하면 오타가 3배가 된다 |
| 안내문 2~3줄 | `1인 1회` 와 `처음 제출만 인정` 은 미리 알려야 분쟁이 없다 |
| 배너별 상태 표시 | 닫힌 평가를 눌러 보고 헛걸음하는 것을 막는다 |

| 뺀다 | 이유 |
|---|---|
| 로그인 | 구글 계정이 없는 사람이 있다. 계정 요구는 곧 응시 불가다 |
| **개인 점수 조회** | 시상은 조 단위다. 점수를 보여주면 **정답을 역산**할 수 있다 |
| 순위 표시 | 조끼리 비교가 현장에서 과열될 수 있다. 발표는 교관이 한다 |
| 재응시 버튼 | 처음 제출만 인정하므로 있으면 혼란만 준다 |

개인 점수를 빼는 결정이 가장 논쟁적이었다. 본인 점수를 궁금해하는 것은
자연스럽지만, **같은 문제지를 뒤 기수가 다시 쓴다.** 점수를 돌려주면
오답을 추려 공유하는 경로가 열린다.

## 교관 화면 — 요구사항

| 요구 | 왜 필요한가 |
|---|---|
| **당일 현황이 기본** | 교관이 보려는 것은 거의 항상 오늘이다. 날짜 고르기부터 시작하면 느리다 |
| 과거 현황은 **따로** | 지난 회차 조회는 가끔 쓴다. 섞으면 실수로 과거를 지운다 |
| 과목 × 조 개폐 | 전체를 한꺼번에 열면 다른 조가 미리 들어간다 |
| **미제출자 번호 표시** | 마감 전에 "누가 안 냈나" 를 알아야 전원 제출을 확인할 수 있다 |
| 번호 사고 복구 | 오입력·재접속 사고는 반드시 생긴다 |
| 설문 결과를 **화면에서** | 구글폼으로 넘어가면 교관이 길을 잃는다 |
| 우수 조 산출 | 당일 시상이므로 즉시 나와야 한다 |

## 문구를 코드에 박지 않는다

부대명·공지·안내문·마감 문구를 **`설정` 시트**에 뒀다.

문구를 고칠 때마다 파일을 수정하고 다시 올려야 한다면, 결국 아무도 고치지
않는다. 시트 칸을 고치는 일이라면 교관이 직접 한다.

## 기각한 요구사항

| 요구 | 기각 사유 |
|---|---|
| 예비군에게 결과 문자 발송 | 연락처 수집이 필요하다. 2번의 원칙과 충돌 |
| 조별 실시간 순위판 | 과열 우려. 진행 중 순위는 교관만 본다 |
| 평가 중 이탈 감지 | 폼 바깥에서 알 수 없다. 기술적으로 불가 |

# 4. 구글폼·앱스스크립트 기반 구조 설계

**2026-10-23 작성**

요구사항을 **어디에 무엇을 둘지**로 옮긴 단계다.

## 설정은 전부 시트에 둔다

스프레드시트 한 권에 탭 넷을 두고, 코드에는 아무 값도 박지 않았다.

| 탭 | 역할 | 교관이 고치는가 |
|---|---|---|
| `설정` | 부대명 · PIN · 조 개수 · 안배정 패턴 · 안내문 | **예** (값 칸만) |
| `과목` | 과목명 · 폼 링크 · 응답 시트 · 만점 · 개방 조 | 처음 1회 |
| `등록` | 날짜별 번호 선점 기록 | 아니오 (자동) |
| `명단` | 사전 명단 (선택) | 쓰면 입력 |

부대가 바뀌어도 **코드는 그대로** 쓰고 시트만 채우면 된다.

> `설정` 탭은 **값(B열)만** 고친다. 항목(A열) 이름을 바꾸면 코드가 찾지 못한다.

## 창구를 공개 / PIN 으로 나눈다

앱스스크립트에 요청 창구를 열 개 뒀다. **경계를 처음부터 못박았다.**

| 창구 | 하는 일 | PIN |
|---|---|---|
| `state` | 열림·닫힘 상태, 폼 주소 | 공개 |
| `claim` | 번호 선점 | 공개 |
| `mine` | 아직 내 번호인지 확인 (읽기만) | 공개 |
| `ping` | PIN 확인 | 필요 |
| `dashboard` | 과목별 현황 · 조별 평균 · 종합 순위 | 필요 |
| `survey` | 설문 집계 | 필요 |
| `lookup` | 번호 조회 | 필요 |
| `toggle` · `groups` | 열기 · 닫기 | 필요 |
| `reset` | 선택 정리 | 필요 |

공개 창구 셋은 **점수를 돌려주지 않는다.** 예비군 화면이 필요한 것은
"지금 열렸는가" 와 "이 번호가 내 것인가" 뿐이다. 점수·현황·명단은 전부 PIN 뒤에 있다.

`mine` 은 **읽기만** 한다. 쓰기까지 허용하면 이 창구로 남의 번호를 가로챌 수 있다.

## 통신 방식

브라우저가 다른 주소로 요청하면 **사전 요청(preflight)** 이 한 번 더 간다.
앱스스크립트는 이것을 제대로 받지 못해 실패한다.

그래서 **`text/plain` 으로 POST** 한다. 이 형식은 사전 요청이 생기지 않는다.
그래도 막히면 **GET 으로 한 번 더** 시도하고, 한 번 막히면 기억해 두고
다음부터는 바로 GET 을 쓴다. 왕복을 두 번씩 반복하지 않는다.

## 같은 요청이 몰릴 때

수백 명이 동시에 태그하면 `state` 가 한꺼번에 들어온다.
그래서 **5초 동안은 계산한 결과를 돌려쓴다.**

| 대상 | 캐시 | 비우는 시점 |
|---|---|---|
| 공개 상태 | 5초 | 열기·닫기·설정 변경 때 즉시 |
| 등록 현황 | 5초 | 등록·해제 때 즉시 |

열고 닫은 것이 5초 늦게 보이면 안 되므로, **바꾸는 순간 캐시를 비운다.**

## 응답 시트를 과목에 붙이는 일

이 지점에서 한 번 크게 틀렸다. 처음에는 "응답 시트가 하나면 그것을 쓴다" 는
식으로 느슨하게 찾았는데, **3과목이 모두 같은 결과를 표시**했다.

지금은 **폼의 질문 제목과 시트 머리글을 대조**해 찾고, 찾은 이름을 `과목`
탭에 적어 둔다. **두 과목이 한 시트를 같이 쓰는 것은 막는다.**
관리자 화면에 `응답 시트:` 로 어느 시트를 쓰는지 표시한다.

# 5. 예비군용 첫 화면 제작

**2026-10-24 작성**

수백 명이 **같은 순간에** 태그한다. 이 화면의 설계 목표는 하나였다 —
**서버를 기다리지 않는다.**

## 뜨는 순서

```
① 카드 태그 → 깃헙이 파일을 바로 내려준다        (즉시)
② 지난번 받아 둔 상태로 배너를 먼저 그린다        (즉시)
③ 서버 응답이 오면 배너 상태만 갈아 끼운다        (1~2초)
```

②가 핵심이다. 서버 응답을 기다렸다면 **수백 명이 흰 화면을 본다.**

서버가 늦으면 안내를 띄우고, **배정된 안(案)의 폼 주소를 이미 아는 경우에만**
응시를 허용한다. 주소를 모르면 잘못된 폼으로 보낼 수 있으므로 기다리게 한다.

## 배너 다섯 가지 상태

| 표시 | 뜻 | 누르면 |
|---|---|---|
| `진행 중` | 내 조가 열렸다 | 번호가 채워진 폼으로 이동 |
| `대기` | 과목은 열렸으나 내 조 차례가 아니다 | 안내만 |
| `마감` | 과목이 닫혔다 | 안내만 |
| `준비 중` | 폼 주소가 아직 없다 | 교관에게 알리라는 안내 |
| `확인 중` | 서버 응답 대기 | 상황에 따라 허용 |

`대기` 와 `마감` 을 나눈 이유 — 예비군이 교관에게 묻는 말이 달라진다.
`대기` 면 기다리면 되고, `마감` 이면 끝난 것이다.

## 번호의 수명

```
조·번 선택 → 확인 누름 → 서버에 선점 → 폰이 기억 → 🔒 잠김
                              │
                              ▼
                     이미 남이 썼으면 거부
```

- 한 번 확정하면 **본인은 바꿀 수 없다.** 교관만 풀어 준다
- 폰이 기억하므로 카드를 다시 태그해도 **번호를 다시 고르지 않는다**
- 접속할 때마다 **아직 내 번호인지 서버에 확인**한다 (9번 항목)
- 폼으로 넘어갈 때 번호가 **미리 채워진다.** 번호 질문을 건드릴 일이 없다

## 폰에서 실제로 터진 문제

아이폰에서 **저장공간 접근이 막히면** (비공개 브라우징 등) 저장을 시도하는
순간 화면 스크립트 전체가 멈춘다. 버튼이 하나도 반응하지 않았다.

이제 저장·읽기를 **전부 예외 처리로 감쌌다.** 저장이 안 되는 폰에서도
화면은 정상 동작하고, 번호를 기억하지 못할 뿐이다.

## 화면에서 덜어낸 것

만들고 나서 지운 것들이다. 전부 "없어도 되는데 눈에 걸리는" 것이었다.

- 번호 아래 `-` 한 줄 (값이 없을 때 남던 자리)
- `등록 완료` 표시 (등록 전에도 떠 있었다)
- `내 번호 1-1 · 배정 A안` 미리보기
- 방패 모양 그림

# 6. 교관 관리자 로그인·권한 기능 구현

**2026-10-25 작성**

## 왜 PIN 인가

| 방법 | 판단 |
|---|---|
| 구글 계정 로그인 | 기각 — 교관 계정을 전부 등록·관리해야 한다. 교대 근무에서 번거롭다 |
| 아이디 + 비밀번호 | 기각 — 사람마다 계정을 만들 이유가 없다. 보는 화면이 같다 |
| **PIN 한 개** | **채택** — 교관끼리 공유. 공용 PC·휴대폰에서 바로 쓴다 |

교관 화면은 **보는 내용이 전부 같다.** 사람을 구분할 필요가 없으므로
계정 체계를 만들지 않았다. PIN 은 `설정` 시트의 `관리자PIN` 칸에 있다.

## 로그인 상태를 서버에 두지 않는다

세션을 만들지 않았다. **요청마다 PIN 을 같이 보낸다.**

```
화면 → [PIN + 요청] → 서버가 PIN 확인 → 처리
```

- 서버가 누가 접속 중인지 기억하지 않는다. 만료·갱신 처리가 없다
- PIN 은 **창을 닫으면 사라지는 자리**에 둔다. 공용 PC 에 남지 않는다
- 로그인 버튼은 PIN 확인만 따로 하지 않고 **바로 현황을 불러온다.**
  왕복이 한 번 줄어 로그인이 빠르다

## 첫 화면의 🔒 도 같은 PIN 을 쓴다

예비군이 번호를 잘못 등록했을 때, 교관이 그 폰에서 **🔒 → PIN** 을 넣으면
번호 재선택 화면이 열린다. 관리자 화면까지 가지 않아도 된다.

PIN 을 모르는 예비군은 번호를 바꿀 수 없다. 이것이 **번호 잠금의 실체**다.

## 한계 — 알고 쓸 것

**내부망 교육용 수준의 보호**다. 다음을 전제로 한다.

| 전제 | 지켜야 할 것 |
|---|---|
| PIN 은 공유 비밀이다 | 예비군에게 노출되지 않게 한다 |
| PIN 이 시트에 적혀 있다 | **응답 스프레드시트를 교관 외에 공유하지 않는다** |
| 기본 PIN 이 있다 | 운용 전에 **반드시 바꾼다** |
| 시도 횟수 제한이 없다 | 짧은 숫자를 쓰지 않는다 |

평가 점수를 다루므로 과한 보호는 아니지만, **대외 공개 시스템 수준은 아니다.**
이 전제가 깨지면 (예: 시트 링크가 돌면) PIN 을 바꾸고 다시 배포한다.

# 7. 조별 평균점수 산출·순위 기능 구현

**2026-10-26 작성**

우수 조를 뽑는 계산이다. **조기 퇴소자가 생겨도 불이익이 없어야** 한다는
조건이 계산 방식을 결정했다.

## 점수 체계

3과목 모두 **20문항 × 5점 = 100점**이다. 과목마다 만점이 같으므로
점수를 그대로 비교할 수 있다. 화면에는 **`점`** 으로 표시한다.

## 두 단계로 계산한다

```
① 과목별 조 점수 =  그 조의 점수 합  ÷  실제 응시인원
② 조 종합 점수   =  과목별 점수의 단순 평균
```

**① 에서 조 정원(10명)이 아니라 실제로 낸 인원으로 나눈다.**
**② 에서 응시인원으로 가중하지 않고 그냥 평균한다.**

이 두 가지가 조기 퇴소 대책이다.

## 조기 퇴소가 왜 불이익이 아닌가

3조 10명 중 3명이 전시동원절차 전에 퇴소한 경우다.

| 과목 | 응시 | 점수 합 | 조 점수 |
|---|---|---|---|
| 안보교육 | 10명 | 850 | 85.0점 |
| 전투부상자처치 | 10명 | 900 | 90.0점 |
| 전시동원절차 | **7명** | 581 | **83.0점** |
| | | **종합** | **86.0점** |

- 퇴소한 3명을 **0점으로 넣지 않는다** → 전시동원절차가 83.0점으로 남는다
- 종합에서 전시동원절차를 **인원수로 깎지 않는다** → 세 과목이 동등하게 들어간다

정원으로 나눴다면 전시동원절차가 58.1점이 되어, 퇴소자가 있는 조는
우수 조에서 자동 탈락했을 것이다.

> 그 대신 **전원 제출을 확인한 뒤 마감**해야 한다. 안 낸 사람이 많은 조가
> 유리해질 수 있으므로, 관리자 화면의 **미제출자 번호**를 보고 마감한다.

## 처음 제출만 인정한다

같은 번호가 여러 번 내면 **가장 먼저 낸 것**만 센다.

마지막 제출을 인정하면 **여러 번 응시해 점수를 올릴 수 있다.**
무시된 제출은 관리자 화면 `중복 제출 목록` 에 뜨고, 조별 현황의 칩에도
금색 테두리와 횟수가 표시된다.

## 순위에서 한 번 틀렸다

1조와 15조가 **둘 다 81.6점**으로 나와 순위를 가릴 수 없었다.
중간 단계에서 반올림한 값으로 순위를 매긴 것이 원인이었다.

지금은 **반올림하지 않은 값으로 순위를 정하고**, 표시만 반올림한다.
같은 점수로 보여도 순위는 정확히 갈린다.

## A안·B안은 한 과목으로 합산

조마다 다른 문제지를 풀지만 **한 과목의 점수로 합친다.** 문제지가 달라도
만점이 같으므로 비교할 수 있다.

배정과 다른 안으로 제출한 사람은 관리자 화면
`배정과 다른 안으로 응시` 표에 따로 뜬다. 점수는 인정하고, 왜 그랬는지만 확인한다.
